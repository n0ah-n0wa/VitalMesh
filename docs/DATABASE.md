# Database

PostgreSQL is VitalMesh's system of record (SPECIFICATIONS.md sections 19–22). This document describes the schema, the invariants the database enforces on its own, the migration workflow, and how the layer is tested.

## Conventions

- **Identifiers** are `uuid` primary keys generated by `gen_random_uuid()`.
- **Timestamps** are `timestamptz`, always UTC. Connections run with `timezone=UTC` and the Go layer normalises every scanned time to UTC.
- **Enumerations** are `text` columns constrained by `CHECK (... IN (...))` rather than PostgreSQL enum types, so adding a value is a plain `ALTER TABLE` and never a non-transactional `ALTER TYPE`.
- **JSON** columns are `jsonb` with a `jsonb_typeof` check so an object column cannot hold an array or scalar.
- **Every constraint and index is named** so that violations can be mapped to stable API error codes and tests can assert on them.
- **Application validation is a convenience, not the guarantee.** Units, value ranges, job transitions and audit immutability are enforced by the database itself.

## Tables

### `users`

| Column | Type | Constraints |
|---|---|---|
| `id` | uuid | primary key |
| `email` | text | not null, non-empty, stored lower case, ≤ 320 chars, unique (`users_email_key`) |
| `password_hash` | text | not null |
| `role` | text | `ADMIN`, `OPERATOR`, `USER` |
| `status` | text | `ACTIVE`, `DISABLED` (default `ACTIVE`) |
| `created_at`, `updated_at` | timestamptz | not null; `updated_at` maintained by trigger |

Users are never deleted, so audit entries and jobs keep a valid actor. Index `users_created_at_id_idx (created_at, id)` backs keyset pagination of the user list.

### `patients`

| Column | Type | Constraints |
|---|---|---|
| `id` | uuid | primary key |
| `external_reference` | text | not null, non-empty, ≤ 128 chars, unique (`patients_external_reference_key`) |
| `date_of_birth` | date | not null, ≥ 1900-01-01 |
| `sex` | text | `FEMALE`, `MALE`, `OTHER`, `UNKNOWN` |
| `status` | text | `ACTIVE`, `INACTIVE`, `DELETED` (default `ACTIVE`) |
| `created_at`, `updated_at` | timestamptz | not null |
| `deleted_at` | timestamptz | present exactly when `status = 'DELETED'` |

Index `patients_created_at_id_idx (created_at, id)` backs keyset pagination of the collection endpoint. Deletion is soft so that jobs and results keep a valid reference.

### `measurement_types`

Lookup table seeded by migration: `code` (primary key, upper case), `canonical_unit`, `min_value`, `max_value` with `min_value < max_value`.

| Code | Unit | Technical range |
|---|---|---|
| `HEART_RATE` | `bpm` | 0 – 300 |
| `BLOOD_PRESSURE_SYSTOLIC` | `mmHg` | 0 – 300 |
| `BLOOD_PRESSURE_DIASTOLIC` | `mmHg` | 0 – 200 |
| `SPO2` | `%` | 0 – 100 |
| `BODY_TEMPERATURE` | `C` | 20 – 45 |
| `BLOOD_GLUCOSE` | `mg/dL` | 0 – 1000 |
| `RESPIRATORY_RATE` | `breaths/min` | 0 – 100 |

The ranges reject values that cannot be a reading at all. They are data validation, not medical thresholds.

### `measurements`

| Column | Type | Constraints |
|---|---|---|
| `id` | uuid | primary key |
| `patient_id` | uuid | not null, references `patients` |
| `type` | text | not null, references `measurement_types` |
| `value` | double precision | not null, finite (`measurements_value_finite_check`) |
| `unit` | text | not null; must equal the type's canonical unit (trigger, `measurements_unit_check`) |
| `recorded_at` | timestamptz | not null |
| `created_at` | timestamptz | not null |
| `source` | text | not null, non-empty, ≤ 64 chars |
| `metadata` | jsonb | not null object, ≤ 4096 bytes |

The trigger `measurements_validate` runs before every insert and update and rejects a unit that does not match the type's canonical unit or a value outside the type's range. The errors carry the constraint names `measurements_unit_check` and `measurements_value_range_check` so they map to API errors like any declared constraint.

Unique `(patient_id, type, recorded_at, source)`: the same reading submitted twice is a conflict, independently of request idempotency.

Access paths required by the specification: `(patient_id, recorded_at)` is `measurements_patient_id_recorded_at_idx`; `(patient_id, type, recorded_at)` is the leading prefix of the unique constraint's index and is served by it. A separate index with those columns was measured to be redundant (same plan, one more index to maintain on the hottest table) and is deliberately absent.

### `processing_jobs`

| Column | Type | Constraints |
|---|---|---|
| `id` | uuid | primary key |
| `patient_id` | uuid | not null, references `patients` |
| `status` | text | `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`, `CANCELLED` |
| `parameters` | jsonb | not null object; the configuration the job ran with, kept for reproducibility |
| `algorithm_version` | text | not null, non-empty |
| `requested_at` | timestamptz | not null |
| `started_at`, `completed_at`, `failed_at`, `cancelled_at` | timestamptz | presence governed by status, see below |
| `error_code`, `error_message` | text | `error_code` required when `FAILED` |
| `attempt_count` | integer | not null, ≥ 0 |
| `created_by` | uuid | not null, references `users` |
| `service_version`, `request_id`, `trace_id` | text | diagnostic metadata (section 94) |
| `lease_expires_at` | timestamptz | processing lease, used by the dispatcher's reconciler |
| `created_at`, `updated_at` | timestamptz | not null |

Status invariants (check constraints): `PENDING` has no lifecycle timestamps; `PROCESSING` has `started_at` only; `COMPLETED` has `started_at` and `completed_at`; `FAILED` has `started_at`, `failed_at` and `error_code`; `CANCELLED` has `cancelled_at`. Timestamps are monotonic: `started_at ≥ requested_at`, `completed_at`/`failed_at ≥ started_at`, `cancelled_at ≥ requested_at`.

The trigger `processing_jobs_enforce_transition` rejects any status change outside the state machine of section 92 (`PENDING → PROCESSING | CANCELLED`, `PROCESSING → COMPLETED | FAILED | CANCELLED`) with the constraint name `processing_jobs_transition_check`. Combined with `UPDATE ... WHERE status = $expected`, transitions are atomic compare-and-set operations.

Indexes required by the specification: `(patient_id, created_at)` and `(status, created_at)`.

### `processing_results`

| Column | Type | Constraints |
|---|---|---|
| `id` | uuid | primary key |
| `job_id` | uuid | not null, references `processing_jobs`, cascades on delete |
| `patient_id` | uuid | not null, references `patients`; copied from the job by the trigger `processing_results_set_patient`, never supplied by the application |
| `measurement_type` | text | not null, references `measurement_types` |
| `window` | text | `1m`, `5m`, `15m`, `1h`, `6h`, `24h`, `7d` |
| `window_start` | timestamptz | not null |
| `statistics` | jsonb | not null object |
| `anomalies` | jsonb | not null array |
| `algorithm_version`, `service_version` | text | not null, non-empty |
| `created_at` | timestamptz | not null |

Unique `(job_id, measurement_type, window, window_start)`. Its index leads with `job_id`, which is the `processing_results(job_id)` access path the specification requires; a separate single-column index would be redundant. Index `processing_results_patient_type_window_idx (patient_id, measurement_type, window, window_start, job_id)` serves the results-of-a-patient endpoint as one index range scan; measured against the join through `processing_jobs`, the denormalised column cut a first page from 1392 to under 100 buffers.

### `audit_logs`

| Column | Type | Constraints |
|---|---|---|
| `id` | uuid | primary key |
| `actor_id` | uuid | references `users`; required when `actor_type = 'USER'`, absent for `SYSTEM` |
| `actor_type` | text | `USER`, `SYSTEM` |
| `action` | text | one of the audited actions (section 43 plus `USER_CREATED`, `RETENTION_RUN`) |
| `resource_type` | text | not null, non-empty |
| `resource_id` | uuid | nullable |
| `request_id` | text | not null, non-empty |
| `metadata` | jsonb | not null object |
| `created_at` | timestamptz | not null |

The trigger `audit_logs_append_only` rejects every `UPDATE` and `DELETE`, so the table is append-only for every database role. Index `(resource_id, created_at)` as required.

### `idempotency_keys`

| Column | Type | Constraints |
|---|---|---|
| `id` | uuid | primary key |
| `user_id` | uuid | not null, references `users` |
| `method`, `path`, `key` | text | not null, non-empty; `key` ≤ 255 chars |
| `request_fingerprint` | text | not null; hash of the canonical request body |
| `status` | text | `IN_PROGRESS`, `COMPLETED` |
| `response_status` | integer | 100–599, present exactly when `COMPLETED` |
| `response_headers` | jsonb | not null, default `{}`; allow-listed headers replayed with the response |
| `response_body` | jsonb | stored response for replays |
| `created_at`, `expires_at` | timestamptz | not null, `expires_at > created_at` |

Unique `(user_id, method, path, key)` serialises concurrent replays even when Redis is unavailable. Index `(expires_at)` supports the expiry sweep, which the gateway runs on a timer for as long as it is up; without it the table would grow for ever, because a key is normally never presented twice.

Only an allow-list of response headers is stored, so nothing per-request or sensitive is persisted: no credentials, no cookies, no request identifiers. Storing them is what lets a replay reproduce the original response rather than only its status and body.

## Migrations

Migrations are plain SQL files under `services/api-gateway/migrations/`, named `NNNNNN_description.up.sql` and `.down.sql`, embedded into the gateway binary and applied with [golang-migrate](https://github.com/golang-migrate/migrate).

```bash
export DATABASE_URL=postgres://vitalmesh:vitalmesh@localhost:5432/vitalmesh?sslmode=disable
api-gateway migrate up        # apply every pending migration
api-gateway migrate down 1    # roll back the most recent migration
api-gateway migrate version   # print the current version and dirty flag
```

- **Locking.** golang-migrate takes a PostgreSQL advisory lock for the duration of a run, so concurrent deployments cannot apply migrations twice.
- **Transactions.** Each file is sent as one multi-statement command, which PostgreSQL executes in an implicit transaction: a failing statement rolls back the whole file. Files must therefore not contain their own `BEGIN`/`COMMIT`, and must avoid statements that cannot run inside a transaction (such as `CREATE INDEX CONCURRENTLY`).
- **Failure state.** If a migration fails, golang-migrate records the version as *dirty* and refuses further runs. Recovery is: inspect the database (the failed file has been rolled back), fix the file, then `api-gateway migrate force <previous version>` and re-run `up`.
- **Rollback strategy.** Every migration ships a `down` file that restores the previous schema. Rolling back destroys the data the migration introduced, so it is a development and staging tool; in production, forward-fix. Destructive changes (dropping or renaming columns) follow expand/contract across two releases so that the running application version and the next one both work against the schema during a rolling upgrade.
- **Execution in deployment.** Migrations run as a separate step before the new application version is rolled out (a Kubernetes `Job` in the deployment pipeline), never at application start-up.

## Go access layer

`services/api-gateway/internal/infra/postgres` uses `pgx/v5` directly with hand-written SQL. There is no ORM: every query is visible, parameterised, and returns explicitly scanned rows. The package provides the connection pool (with `timezone=UTC` and UTC scanning), the migrator, a `WithTx` helper for short transactions, a readiness checker, one repository per table, and a mapping from PostgreSQL error codes and constraint names to domain error kinds: unique violation → conflict, foreign key and check violations → validation with the constraint name as the code, not-null and length/range errors → validation, malformed input (`22P02`) → invalid, serialization failures and deadlocks → unavailable (retryable).

Repositories take a `DB`, which both the pool and a transaction satisfy, so the same code runs standalone or inside `WithTx`. Conventions:

- **Pagination** is keyset-based over `(created_at, id)` (users, patients, jobs), `(recorded_at, id)` (measurements), `(measurement_type, window, window_start)` within a job, or `(measurement_type, window, window_start, job_id)` within a patient (results); every collection query is bounded by `LIMIT` and backed by an index on the same columns, so a page costs one index range scan whatever the collection size. Plans are asserted by an integration test that captures the repositories' real SQL through a pgx tracer and explains it against a seeded schema.
- **Concurrent inserts and keyset cursors.** `created_at` is assigned when a row is inserted, before its transaction commits, so a row can become visible slightly "behind" a cursor a client has already passed; such a row is not returned by that client's remaining pages. Existing rows are never skipped or repeated. This window is a few milliseconds and is the accepted trade-off of timestamp keysets.
- **Retention deletes are bounded.** `Idempotency.DeleteExpired` removes at most `limit` rows per call, walking the `expires_at` index, so the retention job runs many short transactions instead of one long one.
- **Filters** (measurement type and time range) are appended as fixed SQL fragments with numbered placeholders; values only ever travel as parameters.
- **Batch writes** (`CreateBatch` for measurements and results) send one pipelined batch. Through the pool the batch runs in an implicit transaction, so either every row is stored or none is; through a transaction it is part of it. Rows are returned in input order.
- **Conditional updates** (job transitions, patient soft delete, idempotency completion) are compare-and-set statements; when no row matches, the repository reports not-found or conflict by re-reading the current row.
- **Interfaces** are not declared here. Application packages declare the narrow interfaces they consume and these concrete types satisfy them.

## Testing

Integration tests (`go test -tags integration`) run against a real PostgreSQL 16 given by `TEST_DATABASE_URL`, locally via `make dev-db` and in CI via a service container. Each test creates its own schema, applies the migrations into it (connections carry `search_path=<schema>`, which the unqualified names in migrations, trigger bodies and repository SQL resolve through), and drops the schema afterwards, so tests are isolated and run in parallel. Schemas rather than databases keep this fast: dropping a database forces a server-wide checkpoint, dropping a schema does not. They cover migration up from empty and down to empty, atomic rollback of a failing migration, the presence of every required index, each named constraint, the triggers, concurrent compare-and-set transitions, transaction rollback and basic CRUD through the repositories. SQLite is never used.
